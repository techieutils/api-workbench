# API Workbench security model

The renderer is treated as untrusted: it shows responses, imported specs, and markdown from anywhere. Everything powerful lives in the main process behind a narrow bridge. `SECURITY.md` is the public version of this model and the reporting policy; keep the two in step.

## Checklist for a change

- [ ] New IPC uses `handle()`; arguments are validated in main (types, ranges, IDs exist) — never trust renderer input, never accept a file path or command line from it without checking. Work that needs no privilege (parsing, formatting, suggestions) stays out of IPC.
- [ ] No IPC channel, bridge method, or `eval`-like path lets the renderer run a system command or arbitrary code. Spawning processes happens only for the terminal (user-typed) and fixed tools.
- [ ] No secret, token, private key, or credential reaches the renderer, logs, console lines, History, exports, screenshots, generated code, editor suggestions, or CLI output and reports.
- [ ] Untrusted content (responses, imports, specs, markdown) is parsed by fixed grammars and rendered escaped; previews are sandboxed without `allow-scripts`.
- [ ] Request scripts stay in QuickJS: no new host function reaches files, the network, processes, timers, or the vault, and nothing runs a script without the trust check. Editor features over scripts (suggestions, linting, formatting) only parse — no `eval`, `new Function`, or `vm` — and parsers run with fixed options.
- [ ] Text inserted into a terminal: `promptText(...)`; each value: `shellQuote`/`shellWord`. Test with `'`, `;`, `|`, `$()`, backticks, newlines, and escape sequences.
- [ ] No inline scripts/styles; no CSP loosening. Network stays in main.
- [ ] Links open externally only through the app's confirmed path — `openWebLink` in `main.ts`, the one `shell.openExternal` call, which passes only `http:`, `https:`, and `mailto:` (never `file:`, `smb:`, or another app's scheme, which can start a program); no new permissions granted.
- [ ] A new parser of text from someone else (an import format, a file type, a response view) gets a target and a seed in `scripts/fuzz/` (`npm run test:fuzz`, run in CI).
- [ ] A regular expression that comes with a workspace, collection, mock, or specification is compiled with `untrustedRegExp` (common `regex-safety.ts`), never `new RegExp`, so a pattern that can backtrack exponentially is refused instead of freezing a process.
- [ ] A path that comes with shared content (a `.http` file, a collection) is read only from inside its project, resolved with `realpath` so links cannot leave it.
- [ ] VS Code extension: no new setting that names a program or path, or turns on code execution, unless `machine`-scoped; nothing runs in untrusted workspaces; it runs only the CLI, with `execFile`/`spawn` and argument arrays, never a shell. Webviews (`src/panels.ts`) keep `default-src 'none'` with a nonce script, `enableCommandUris: false`, and accept only the fixed `Action` names; `src/webview/` renders with `textContent`, never HTML. A vault password typed in VS Code stays in memory for the window and goes only to the CLI's environment (`API_WORKBENCH_VAULT_PASSWORD`).
- [ ] CLI: a new option never takes a secret as its value (read stdin or an environment variable instead); output passes through the same redaction as existing commands.
- [ ] New dependency: needed, maintained, licence-compatible, ideally already in the lockfile; `npm audit --omit=dev --audit-level=high` clean. A dependency the CLI uses must bundle into its single file.
- [ ] Workflows: least `permissions` per job; secrets only in the steps that need them; nothing published from a tag push alone — publishing waits for a reviewed release; actions by major tag, downloaded tools pinned by version and SHA-256.
- [ ] Tests use made-up values; real-looking public samples carry `// gitleaks:allow`.
- [ ] A change to the model above is reflected in `SECURITY.md`'s Security design and scope.

Report vulnerabilities per `SECURITY.md`, never in public issues.
