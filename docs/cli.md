# Command line

The `api-workbench` command does from a terminal what the app does in its window. It runs a collection's requests and tests in a CI pipeline, and fails the build when one fails. It sends a single request and shows the response. It also manages a workspace's collections, environments, credentials, specifications, mock servers, history, and Git sync.

It sends requests exactly as the app does: the same variables, authentication, HTTP settings, captures, cookies, and assertions. It reads and writes the same files the app does, so a request saved in the app is the one the command line runs, and a change made from the command line shows up in the app.

## Quick start

```sh
# Get the command line: one file, which needs only Node.js 22.19 or later.
curl -fsSL -o api-workbench.cjs \
  https://github.com/techieutils/api-workbench/releases/latest/download/api-workbench-cli.cjs

# Run a team workspace folder's tests, as CI would.
node api-workbench.cjs run ./api -e Staging

# Or work with the workspaces you have in the app.
node api-workbench.cjs workspace list
node api-workbench.cjs request send "Get order" -e Staging
```

Every command explains itself with `--help`: `node api-workbench.cjs --help` lists them all, and `node api-workbench.cjs environment --help` explains one. A mistyped name says what you probably meant, such as _No environment “Stagin”. Did you mean “Staging”?_

## Install

The command line needs [Node.js](https://nodejs.org) 22.19 or later. Get it from npm, or as one file from a release.

### With npm

It is published to GitHub Packages as [`@techieutils/api-workbench-cli`](https://github.com/techieutils/api-workbench/pkgs/npm/api-workbench-cli), with no dependencies. GitHub asks for a token to install from its registry, even for public packages: create a [personal access token (classic)](https://github.com/settings/tokens) with `read:packages`, then tell npm about the registry, in `~/.npmrc` or a project's `.npmrc`:

```ini
@techieutils:registry=https://npm.pkg.github.com
//npm.pkg.github.com/:_authToken=${GITHUB_TOKEN}
```

npm reads the token from the `GITHUB_TOKEN` environment variable, so it stays out of the file. Then:

```sh
npm install --global @techieutils/api-workbench-cli
api-workbench --version
```

`npx @techieutils/api-workbench-cli <command>` runs it without installing, and `npm install --save-dev @techieutils/api-workbench-cli` pins it in a project. Pre-releases are under the `next` tag. With npm, type `api-workbench` wherever this page has `node api-workbench.cjs`. The package's [README](https://github.com/techieutils/api-workbench/blob/main/packages/api-workbench-cli/README.md) has a command reference.

### As one file

The same command line is one JavaScript file, `api-workbench-cli.cjs`, attached to every [release](https://github.com/techieutils/api-workbench/releases). It needs nothing but Node.js: no install step, no other packages, and no token.

To check the download against the release's `SHA256SUMS`, as for the app (see [Check a download](installation.md#check-a-download)), keep its original name until it is checked:

```sh
base=https://github.com/techieutils/api-workbench/releases/latest/download
curl -fsSLO "$base/api-workbench-cli.cjs" -O "$base/SHA256SUMS"
shasum -a 256 --check --ignore-missing SHA256SUMS   # sha256sum on Linux; prints OK
mv api-workbench-cli.cjs api-workbench.cjs
```

To type `api-workbench` instead of `node api-workbench.cjs`, keep the file somewhere permanent and add an alias to your shell's profile:

```sh
alias api-workbench='node ~/bin/api-workbench.cjs'
```

The command line is released with the app, so their versions match: `--version` prints it. In CI, pin a release (`…/releases/download/v1.2.0/api-workbench-cli.cjs`) so a new version never changes your build without a commit. From a clone of the repository, `npm run cli -- <command>` runs the current source.

## What it works on

| Where                                                                                                                          | How                                                         | Used by                         |
| ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------- | ------------------------------- |
| One of the app's workspaces                                                                                                    | `-w`, `--workspace <name or id>`; the active one by default | Every command                   |
| A [team workspace](team-workspaces.md) folder, such as one in your repository                                                  | `--dir <folder>`, or the folder itself for `run` and `list` | Every command                   |
| A collection file in any format the app imports: API Workbench, Postman, Insomnia, Bruno, Hoppscotch, OpenAPI, HAR, or `.http` | The file itself                                             | `run` and `list`                |
| A specification file                                                                                                           | The file itself                                             | `spec show`, `lint`, `generate` |

The app's workspaces are in its data folder, the same one the app uses: `~/Library/Application Support/API Workbench` on macOS, `%APPDATA%\API Workbench` on Windows, and `~/.config/API Workbench` on Linux. Give `--data-dir <folder>`, or set `API_WORKBENCH_DATA_DIR`, for another one, such as a test profile.

Changes are written by the same code the app saves with, so the files come out exactly as the app writes them, and an open app picks them up as it does any change made outside it. A team folder is changed as a teammate would change it: only shared files, with no secret values and no history of its own.

```sh
node api-workbench.cjs list ./api           # a team folder
node api-workbench.cjs list -w "Shop API"   # one of the app's workspaces
node api-workbench.cjs list ./api --json    # for scripts
node api-workbench.cjs list ./api --tag smoke   # what run --tag smoke would send
```

`list` shows the collections, requests, and environments. `list --json` gives each request's id, name, folder, method, protocol, and whether the command line runs it (`runnable`); it never includes URLs or variable values.

## Run tests

```sh
node api-workbench.cjs run ./api --collection Orders --environment Staging --report-junit results.xml
```

`run` sends the chosen requests in explorer order, runs their tests and [captures](variables.md#capture-values-from-responses), and prints each result as it comes. Values a request captures are available to the requests after it, and cookies set by a response are sent on later ones, as in a collection run in the app.

| Option                         | What it does                                                                                                                                                                                                          |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-c`, `--collection <path>`    | Run a collection or folder, such as `Orders` or `Orders/Refunds`. Repeat for several; all by default                                                                                                                  |
| `-r`, `--request <name or id>` | Run only these requests (repeatable)                                                                                                                                                                                  |
| `-t`, `--tag <tag>`            | Run only requests with this [tag](requests.md#tags) — repeatable, or `a,b` — any of them                                                                                                                              |
| `--all-tags`                   | With several `--tag`, run only requests with all of them                                                                                                                                                              |
| `--exclude-tag <tag>`          | Leave out requests with this tag (repeatable, or `a,b`); it wins over `--tag`                                                                                                                                         |
| `-e`, `--environment <name>`   | The environment to use; the first one by default                                                                                                                                                                      |
| `-v`, `--var <name=value>`     | Set a variable, over the environment's value (repeatable)                                                                                                                                                             |
| `-v`, `--var <name>`           | Set a variable from the process environment variable of the same name — the way to give secrets                                                                                                                       |
| `-d`, `--data <file>`          | Run once per row of a CSV, JSON, YAML, or XML file — see [Run with a data file](runner.md#run-with-a-data-file)                                                                                                       |
| `--uploads <file>`             | The files requests send, as JSON: `{"<request>": "<path>"}` for a file body, `{"<request>": {"<field>": "<path>"}}` for a form's file fields; requests by name or id, paths relative to the JSON file                 |
| `--allow-host <host>`          | Send only to this host (repeatable; `*.example.com` for its subdomains), checked after variables and pre-request scripts; a request to any other fails, unsent                                                        |
| `--list-hosts`                 | Print, as JSON, the hosts the chosen requests would go to — for every data row, with the environment and `-v` values — and send nothing; requests whose host comes from an earlier capture are listed as `unresolved` |
| `-n`, `--iterations <count>`   | Run every request this many times                                                                                                                                                                                     |
| `--delay <ms>`                 | Wait between requests                                                                                                                                                                                                 |
| `--timeout <ms>`               | Request timeout, over the workspace's                                                                                                                                                                                 |
| `--bail`                       | Stop at the first failure                                                                                                                                                                                             |
| `--allow-scripts`              | Run the requests' pre-request and post-response [scripts](scripts.md)                                                                                                                                                 |
| `--skip-scripts`               | Run the requests without their scripts                                                                                                                                                                                |
| `-k`, `--insecure`             | Do not verify TLS certificates                                                                                                                                                                                        |
| `--report-junit <file>`        | Write JUnit XML, which CI systems show as test results                                                                                                                                                                |
| `--report-json <file>`         | Write a JSON report                                                                                                                                                                                                   |
| `--quiet`                      | Print only failures and the summary                                                                                                                                                                                   |
| `--no-color`, `--color`        | Plain or coloured output; plain is the default when `NO_COLOR` is set or output is not a terminal                                                                                                                     |
| `-w`, `--workspace <name>`     | Run one of the app's workspaces instead of a folder or file                                                                                                                                                           |

Tags choose requests after `-c` and `-r`: a run with `--tag` sends the chosen requests that have the tag, on themselves or on their collection or a folder they are in. A tag none of them has stops the run with exit code 2 and the tags there are (_Did you mean “smoke”?_), so a typo never quietly runs nothing. The JSON report records the filter as `tags`, such as `"smoke, not slow"`. `list` takes the same options, to see what a run would send, and shows each request's tags; `request show` shows them too, and `request create --tag smoke` tags a new request.

A run whose requests have [scripts](scripts.md) stops with exit code 2 until you choose `--allow-scripts` or `--skip-scripts`, since scripts run code from the workspace. Script tests count with the request's tests, and what scripts log is printed under the request. `request send` takes the same two options.

A request **passes** when all its tests pass. A request without tests passes when its status is from 200 to 399. Any request that gets no response fails. Live protocol requests (WebSocket, gRPC, and the others) are listed but not run.

Press <kbd>Ctrl C</kbd> to stop a run. The request in flight is cancelled and counted as skipped, and the summary and reports still cover the requests that finished. Press it again to quit at once, without reports.

### Reports

**JUnit XML** (`--report-junit`) has a test suite for each collection, or for each collection and iteration when there are several. Each request sent is a test case, with a `failure` for failing tests and an `error` when no response came. GitHub Actions, GitLab, Jenkins, and Azure DevOps all show it as test results.

**JSON** (`--report-json`) is for tools and dashboards:

| Field                           | What it holds                                                                                 |
| ------------------------------- | --------------------------------------------------------------------------------------------- |
| `passed`                        | Whether every request passed                                                                  |
| `summary`                       | Requests sent, failed, and skipped; tests and failed tests; time taken                        |
| `metrics`                       | Latency (average, percentiles, standard deviation), throughput, and error counts              |
| `results`                       | Each request sent: name, folder, method, URL, status, time, tests, captures, and any error    |
| `source`, `environment`, `data` | What ran: the workspace or file, the environment's name, and the data file's rows and columns |
| `interrupted`                   | `true` when <kbd>Ctrl C</kbd> stopped the run                                                 |

With `--reporter junit` or `--reporter json` and no file name, the reports are written to `api-workbench-junit.xml` and `api-workbench-report.json` in the current folder.

## Load tests

Any load setting makes `run` a performance run, as the [Runner](runner.md)'s **Performance** mode does. The chosen requests are sent over and over for `--duration` seconds, either `--concurrency` at a time or at `--rps` a second. `--mode benchmark` instead sends every request `-n` times as fast as it can.

```sh
node api-workbench.cjs run ./api -c Orders -e Staging \
  --duration 30 --concurrency 10 --p95 500 --max-error-rate 1 --report-junit load.xml
```

| Option                 | What it does                                                       |
| ---------------------- | ------------------------------------------------------------------ |
| `--mode <mode>`        | `collection` (the default), `benchmark`, or `performance`          |
| `--concurrency <n>`    | Requests in flight at once, from 1 to 50                           |
| `--duration <seconds>` | How long a performance run lasts; 10 by default                    |
| `--rps <rate>`         | Start this many requests a second, whatever is still in flight     |
| `--ramp-up <seconds>`  | Reach full concurrency or rate over this time                      |
| `--warmup <n>`         | Unmeasured requests first                                          |
| `--max-requests <n>`   | Stop after this many; 10,000 by default                            |
| `--p95 <ms>`           | Fail when the 95th percentile latency is above this                |
| `--max-error-rate <%>` | Fail when more than this percentage of requests fail; 0 by default |
| `--min-rps <rate>`     | Fail when throughput is below this                                 |

A load test does not print a line per request. It shows its first few failures as they happen, then the throughput, latency percentiles, failures by kind, and each threshold with its result:

```text
Performance: 3 requests for 30 s, 10 at a time

8412 requests in 30.0 s · 280.4 a second · 0 failed (0.00%)
Latency: average 34 ms · p50 31 ms · p90 52 ms · p95 61 ms · p99 98 ms · max 240 ms
  ✓ Error rate (%): 0 (limit 1)
  ✓ p95 latency (ms): 61 (limit 500)
Passed
```

It exits with `1` when a threshold is missed. Its JUnit report has a test case per threshold, so CI shows which limit failed, and its JSON report has the configuration, metrics, thresholds, a timeline, and errors grouped by message, in place of every request. Load tests take no data file.

> [!WARNING]
> A load test sends many requests quickly. Test APIs you own or are allowed to test, and prefer a staging environment. One machine is the load generator, so its CPU and network limit how much load it can produce — see [Load test an API](guides/load-test-an-api.md).

## Send a request

```sh
node api-workbench.cjs request send "Get order" -e Staging -i
```

```text
200 OK  84 ms · 412 B · HTTP/1.1
GET https://staging.example.com/orders/42

content-type: application/json
set-cookie: <hidden>

{
  "id": 42,
  "total": 18.5
}

✓ status 200
captured order_id
```

`request send` sends one request as **Send** does in the app. It prints the status, time, size, and body (JSON is indented), then the request's tests and captures. It exits with `1` when its tests fail, or, for a request without tests, when its status is outside 200–399.

| Option                                       | What it does                                                                                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-e`, `--environment`                        | The environment to use; the workspace's active one by default                                                                                     |
| `-v`, `--var <name=value>`                   | Set a variable for this send (repeatable); `-v name` reads `$name`                                                                                |
| `-i`, `--include`                            | Show the response headers                                                                                                                         |
| `--no-body`                                  | Leave the body out                                                                                                                                |
| `--body-only`                                | Print only the body, exactly as it came, for a pipe or a file                                                                                     |
| `--json`                                     | Print the status, headers, body, tests, and captures as JSON                                                                                      |
| `--no-save`                                  | Leave the workspace as it was (see below)                                                                                                         |
| `-k`, `--insecure`                           | Do not verify TLS certificates                                                                                                                    |
| `--timeout <ms>`                             | Request timeout, over the workspace's                                                                                                             |
| `--binary-file <path>`                       | The file a file body sends (20 MB at most), read for this send only                                                                               |
| `--form-file <field>=<path>`                 | The file for a form's file field, by its name; give one for each                                                                                  |
| `--allow-host <host>`                        | Send only if it goes to one of these hosts (repeatable), after variables and scripts; otherwise exit 2, unsent                                    |
| `--file <file>`                              | Send a request of a collection file instead (see below)                                                                                           |
| `--base-dir <folder>`                        | The folder a `.http` file's `< ./path` files are relative to, instead of the file's own — for a copy of it, such as an editor's unsaved text      |
| `-w`, `--workspace` or `--dir` with `--file` | Fill a collection file's `{{variables}}` from that workspace's environment (`-e`, or the one it uses), under the file's own `@name = value` lines |

A file body, or a form's file field, is sent from a file you give with each send — the request saves only the file's name, as the app does. `run --uploads <file>` gives a run its files, from a JSON file that can sit beside the workspace in your repository; see [Run tests](#run-tests):

```sh
node api-workbench.cjs request send "Upload avatar" --form-file avatar=photo.png
node api-workbench.cjs request send "Import" --binary-file export.csv
```

```sh
node api-workbench.cjs request send "Get order" --body-only | jq .total
node api-workbench.cjs request send "Download invoice" --body-only > invoice.pdf
```

In one of the app's workspaces the send is kept in [History](history.md), and the values it captures go into the environment for the next request to use, as after a send in the app. `--no-save` leaves the workspace unchanged. A send never changes a team folder given with `--dir`.

`--file <file>` reads a collection file in any format the app [imports](import-export.md) — a `.http` file, a cURL command, a Postman collection — instead of a workspace, and never changes it. `request list`, `show`, `send`, and `code` all take it. A request is named by its name, or by its position in the file (`1`, `2`, …) when the format has no ids; the file's variables (`@name = value` in a `.http` file) are its environment. No app data is needed.

```sh
node api-workbench.cjs request list --file orders.http
node api-workbench.cjs request send 2 --file orders.http -i
node api-workbench.cjs request send 2 --file orders.http --dir . -e Staging   # {{variables}} from Staging
```

In a `.http` file, a body of one `< ./path` line sends that file, and a `multipart/form-data` body's `< ./path` parts send files as form fields, as in VS Code's REST Client and JetBrains' HTTP Client. Paths are relative to the `.http` file (or `--base-dir <folder>`) and read when the request is sent, by `request send --file` and `run`; `--binary-file` and `--form-file` send other files instead. A file the `.http` file names must be inside its project — the repository it is in (the nearest folder above it with `.git`), or its own folder outside a repository — so `../fixtures/data.json` works, but an absolute path elsewhere, `../` above the repository, or a link that points out of it is refused: a repository you open cannot send your keys or other files. To send such a file, name it yourself with `--binary-file` or `--form-file`, or list it in a run's `--uploads` file. A path's `{{variables}}` are filled in as the request's are — the environment, the file's `@name = value` lines, `-v`, a data file's row, and built-ins — and `<@ ./path` fills in those in the file's text too, as REST Client does. To use an environment variable of your shell, `-v name` reads `$name`:

```sh
stage=staging node api-workbench.cjs run uploads.http -v stage   # < ./data/{{stage}}/users.csv
```

## Manage a workspace

Each command below takes `-w` or `--dir` to say which workspace it works on, `--json` to print JSON for scripts, and `--help`. Deleting anything asks for `--yes`. A workspace always keeps at least one request and one environment, as in the app.

Give a request by its name, by `Folder/Name` when several share a name, or by its id (`request list --json` shows ids). Give a collection or folder by its path, such as `Orders` or `Orders/Refunds`.

### Workspaces

| Command                               | What it does                                                                      |
| ------------------------------------- | --------------------------------------------------------------------------------- |
| `workspace list`                      | The app's workspaces; `*` marks the active one                                    |
| `workspace show [<workspace>]`        | Its collections, requests, environments, specifications, and mock servers         |
| `workspace create <name>`             | A new workspace, started as the app starts one                                    |
| `workspace rename <workspace> <name>` | Rename it                                                                         |
| `workspace use <workspace>`           | Make it the active workspace, as the switcher does                                |
| `workspace delete <workspace> --yes`  | Deleting a team workspace removes it from this device and keeps its shared folder |


The secret is read from standard input or an environment variable, never from an argument, so it stays out of shell history and process lists, and no command ever prints it. Client certificates have their own commands, [below](#client-certificates).

The command line opens the [API Workbench vault](credentials.md#the-api-workbench-vault) with its password, from `API_WORKBENCH_VAULT_PASSWORD` or typed at a terminal. Credentials the app keeps in the system's credential store (the macOS Keychain, Windows DPAPI, or a Linux keyring) can be opened only by the app itself, so manage those there. Team folders keep no credentials: each teammate's are in their own vault.

> [!NOTE]
> `run` does not send requests that use **Saved credential**. In CI, put the secret in a variable instead — see [Use it in CI](#use-it-in-ci).

## What is never printed

The command line follows the app's rules for logs, since terminal output and CI logs are often widely read:

- Credential values are never printed, and never taken as an argument. A request's own auth secrets — tokens, passwords, signing keys, client secrets, OAuth 2.0 access and refresh tokens — come from environment variables (`--auth-secret-from-env`, `--auth-fields-from-env`); `request show --json` says only which are saved, and `request token` prints when a token expires, never the token.
- Values whose names look secret (tokens, passwords, keys, sessions, `Authorization` and `Cookie` headers) show as `<hidden>` in `environment show`, `request show`, response headers, and JSON output.
- URLs leave out their user name, password, and secret-looking query values, in output, reports, and History.
- Reports show names, URLs, statuses, timings, and test results, never headers, bodies, or variable values. A failing test shows the value it found, unless the test reads something secret-looking.
- Generated code redacts secret-looking headers, query values, and fields, and shows saved credentials as placeholders.
- Text from a response, a specification, or a workspace is printed without the control characters that could rewrite a terminal's screen.

## Use it in CI

The command line fits any CI system that runs Node.js. Keep a team workspace folder in your repository, so the requests your team edits in the app are the ones CI runs. Then download the file in the pipeline, run it, and publish its JUnit report. [Run API tests in CI](guides/run-api-tests-in-ci.md) has complete setups for GitHub Actions, GitLab CI, Jenkins, and Azure DevOps.

[Team workspaces](team-workspaces.md) never contain secrets, and `run` does not read the vault. Put each secret in a variable instead, such as `Bearer {{api_token}}` in the request, and give it from your CI system's secret store:

```sh
api_token="$STAGING_TOKEN" node api-workbench.cjs run ./api -e Staging -v api_token
```

`-v api_token`, without `=`, reads the value from the `api_token` environment variable, so the secret never appears on the command line. A request that uses **Saved credential** fails with a message saying to do this.

## Troubleshooting

| Message                                                                    | What to do                                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `TypeError: Cannot read properties of undefined (reading 'bind')` on start | Node.js is older than 22.19. | _No API Workbench data in …_                                               | Open the app once so it creates its data folder, give `--data-dir`, or use `--dir` for a team folder                                                                                                                                                          |
| _… a saved credential, which lives in the app's vault_                     | Run it from one of the app's workspaces (`-w`), or a team folder the app on this computer has open, with the vault's password in `API_WORKBENCH_VAULT_PASSWORD`, or put the secret in a variable and give it with `--var` — see [Use it in CI](#use-it-in-ci) |
| _… encrypted with the system's credential store by the desktop app_        | That vault opens only in the app: manage those credentials in its **Credentials** screen                                                                                                                                                                      |
| _2 requests are named “…”_                                                 | Give the folder too, as `Folder/Name`, or the request's id from `request list --json`                                                                                                                                                                         |
| _… a workspace keeps at least one_                                         | Create another request, collection, or environment before deleting the last one                                                                                                                                                                               |
| _This mock serves HTTPS with the app's own certificate authority_          | Start it in the app, or give it your own certificate and key files in the app's mock settings                                                                                                                                                                 |
| _“…” looks secret, and team folders never hold secret values_              | Give the value with `run --var` in CI, or set it in the app, where it stays on your device                                                                                                                                                                    |
